## 0. 结论先行

**标签的问题不在定义，在实现。** `docs/concept-model.md:59` 早已把标签定为「作用域与横切属性」——所以不是「标签应该变成属性」还没做，而是**概念层定成属性了，实现层没跟上**。

根因一句话：**标签的存储是结构化的（`memo_tags` 表），但写入完全寄生在 Markdown 正文上，且由两套互相打架的正则去「猜」。**

故障分三层，从深到浅：

| 层 | 问题 | 后果 |
|---|---|---|
| 写入链路 | 客户端弱正则的结果**覆盖**服务端强正则 | 中文标点后的标签、层级标签静默丢失 |
| 编辑链路 | 改正文**永不再算**标签 | 正文与标签系统永久脱节 |
| 提取规则 | 不隔离 Markdown 字面量（代码块/链接/标题） | 垃圾标签持续注入 |
| 呈现层 | 侧栏标签树是**唯一没有图标尺寸约束**的组件，且历次打磨都被显式跳过 | 「一塌糊涂」的直接观感 |

**关于你的两个直觉**：

1. **「标签应该是属性」——方向对，但结论要修正。** 真正的病不是「标签出现在正文里」，而是「结构化表被一套不靠谱的文本提取喂养」。正文里写 `#tag` 是这个品类的肌肉记忆，不该砍；该修的是物化（materialize）过程。详见 §3.1 的路线对比。
2. **「任务也应该是笔记的属性」——这一条建议维持现状，理由见 §2.2。** 痛点是真实的，但药方是「加宽那道门」，不是把任务降格。概念模型的红线已经覆盖这个方向。

## 1. 现状盘点

### 1.1 标签的完整生命周期

```
正文 "#工作/项目A"（Markdown 纯文本，唯一输入形态）
        │
        ├─ 客户端正则 extractTags        apps/web/src/lib/memo.ts:10        ← 弱
        └─ 服务端正则 extractTags        packages/domain/src/tags.ts:61     ← 强
                    │
                    ▼
        payload.tags: string[]           （写进 memos.payload，长期驻留）
                    │
                    ▼
        memo_tags 表 (memo_id, tag, user_id)    packages/db/src/schema/memos.ts:127-147
                    │
        ┌───────────┼────────────┬──────────────┐
        ▼           ▼            ▼              ▼
   侧栏标签树    时间线筛选   重命名/删除    stats 计数
   (层级聚合)    (前缀匹配)   (改写正文)    (扁平 COUNT)
```

关键设计事实（这些**是对的**，应该保留）：

- **存储结构化**：`memo_tags` 独立表，主键 `(memo_id, tag)`，带 `(user_id, tag, memo_id)` 索引，支持层级、计数、筛选、批量重命名
- **层级语义完整**：`/` 为路径分隔符，`工作` 命中 `工作` 与 `工作/项目A`（前缀匹配，`tags.ts:76-78`）
- **重命名是子树的**：`工作` → `知识/工作` 时 `工作/项目A` → `知识/工作/项目A`，且不误伤 `工作者`（`tags.ts:272-287`）
- **重命名/删除会同步正文**：`rewriteTagInContent` / `removeTagFromContent`（`tags.ts:463-492`），并伴随 revision、embedding 重索引、SSE、webhook，与普通编辑对齐

也就是说：**下游（存储与消费）是健康的，病灶全在「正文 → 标签」这一段。**

### 1.2 病灶一：两套正则，弱的那套赢

系统里有四个不同来源的标签字符集定义：

| 位置 | 正则 / 字符集 | 支持 `/` |
|---|---|---|
| 服务端提取 | `packages/domain/src/tags.ts:61` `/(^\|[^\p{L}\p{N}_\-/])#([\p{L}\p{N}_\-/]+)/gu` | ✅ |
| 客户端提取 | `apps/web/src/lib/memo.ts:10` `/(^\|\s)#([\p{L}\p{N}_-]+)/gu` | ❌ |
| 编辑器高亮 | `apps/web/src/lib/tag-highlight.ts:8` `(^\|[\s(（[>「])#([\p{L}\p{N}_-]+)` | ❌ |
| 编辑器补全 | `apps/web/src/lib/tag-autocomplete.ts:10` `^[\p{L}\p{N}_-]*$` | ❌ |

前后端两套提取规则**实测不一致**（同一批中文典型写法，8 例中 5 例结果不同）：

| 正文 | 客户端提取 | 服务端能提取 |
|---|---|---|
| `……工具本身。#随手记` | `[]` | `["随手记"]` |
| `本周复盘。#工作` | `[]` | `["工作"]` |
| `记录一下 #工作/项目A` | `["工作"]`（层级被截断） | `["工作/项目A"]` |
| `打卡。#健身 #读书` | `["读书"]`（丢一个） | `["健身","读书"]` |
| `结尾（#备注）` | `[]` | `["备注"]` |

差异集中在**中文标点之后**与**层级路径**——而中文写作没有空格分词，`。#标签` 恰恰是最自然的写法。

**谁说了算？客户端。** `packages/domain/src/memos.ts:137`：

```ts
const tags = normalizeMemoTags(payload.tags ?? extractTags(input.content));
```

`??` 只对 `null` / `undefined` 回落。而编辑器在**每次输入时**就把客户端正则的结果写进草稿（`memo-composer.tsx:213`），提交时总是带 payload（`memo-submission.ts:14`）。于是客户端那个更弱的结果优先级更高，**服务端更强的提取永远没机会跑**。

**后果：同一句中文，用网页输入和用 API/agent 输入，得到的标签不一样。**

| 入口 | 生效的正则 |
|---|---|
| 网页 composer 创建 | 客户端（弱） |
| IM / MCP / agent / 直接 POST | 服务端（强） |
| 导入 bundle | 取决于 bundle 是否带 tags |

**实证**（mini 上运行中的 dev 实例，只读取证）：

```
正文：      ……好的工具应该让人忘记工具本身。#随手记
payload.tags: []
memo_tags 行: 0
```

标签明明白白写在正文里，系统里**不存在**。这就是「侧栏看着不对劲」的深层来源：不是显示得难看，是**该有的没有**。

### 1.3 病灶二：编辑正文永不再算标签

`packages/domain/src/memos.ts:711-736` 的更新路径：

```ts
const nextPayload =
  input.payload !== undefined
    ? normalizeMemoPayload(input.payload)
    : normalizeMemoPayload(existing.payload);   // ← 从已存 payload 展开，含旧 tags
...
const tags = metadataChanged
  ? normalizeMemoTags(nextPayload.tags ?? extractTags(nextContent))
  : [];
```

创建时 `payload.tags` **总是**被赋值（`memos.ts:137-138`，哪怕是空数组）。所以更新时 `nextPayload.tags` 永远是「定义好的数组」，`??` **永不回落**，`extractTags` 在编辑路径上是死代码。

而网页的两条编辑路径都只提交 content、不提交 payload：

- 卡片内联编辑：`memo-card.tsx:279-282`
- 详情页编辑：`memo-detail-page.tsx:173`

**净效果**：标签只在创建那一瞬间确定一次，之后：

- 在正文里**新增** `#新标签` → 侧栏不出现
- 在正文里**删掉** `#标签` → 侧栏仍显示，计数不减
- 正文与标签系统**永久脱节**，且没有任何机制提示不一致

### 1.4 病灶三：Markdown 字面量「双标」

提取时**完全不看** Markdown 结构，但重命名/删除时**会**保护字面量。这个不对称造成两类问题：

**提取侧（无保护）——实测结果**（下表为服务端较强正则的行为；客户端正则同样不看 Markdown 结构，只是边界更窄，故两侧都会注入垃圾标签，但注入的集合不同）：

| 正文 | 被提取成标签 |
|---|---|
| ` ```css .card { color: #fff; } ``` ` | `fff` |
| `[安装](#install)` | `install` |
| `<a href="#top">` | `top` |
| `##待办事项`（中文习惯不带空格） | `待办事项` |
| `修复了 #123 和 #456` | `123` |

**删除侧（有保护）**：`removeTagFromContent` 走 `rewriteOutsideLiteralSegments`（`tags.ts:576-583`），把围栏代码块、行内代码、URL 标记为 literal 不改写。

**净效果**：垃圾标签会**持续注入**（每粘贴一次含 CSS 色值的代码就注入一次），而侧栏删除只清标签表、**不清正文**——正文里的 `#fff` 永远留着，下次同内容再入库又原样回来。用户看到「删了但没删干净」的观感。

这是设计取舍造成的，不是 bug——**但取舍方向是反的**：应该在提取时就隔离字面量，而不是在改写时才隔离。

### 1.5 病灶四：renameTag 的 LIKE 未转义（正确性 bug）

`tags.ts:227` 与 `:265` 用 LIKE 前缀选子树：

```ts
or(eq(memoTags.tag, from), sql`${memoTags.tag} LIKE ${`${from}/%`}`),
```

`_` 是标签字符集里的合法字符（正则明确允许），但在 LIKE 里 `_` 是**单字符通配符**。所以：

- 重命名 `a_b` 时，`axb/foo` 这类**无关标签**也会被选中
- 随后 `tags.ts:294` 的 `${to}${row.tag.slice(from.length)}` 会基于错误行拼出新标签

对照：列表筛选 `memos.ts:343` 是用 `escapeLike` + `ESCAPE '\'` 的，属实现不一致。

触发条件窄（标签里含 `_` 且存在同形碰撞），但一旦触发是**静默的跨标签数据损坏**——建议随本方案一并修掉。

### 1.6 病灶五：统计口径互相打架

同一个「标签数」，三个地方三个口径：

| 位置 | 口径 | 结果 |
|---|---|---|
| 侧栏顶部统计格 `flaremo-explorer.tsx:137` | `stats.tags.length`（**扁平**，`memos.ts:542-561` 的 `COUNT(*)` groupBy） | 按完整路径去重 |
| 侧栏标签树 `tags.ts:138-183` | 层级聚合，父节点**含全部后代**去重计数 | 行数与数字都对不上统计格 |
| 标签筛选 | 前缀匹配（`工作` 命中 `工作/项目A`） | — |

用户看到的「标签 5」，下面却列着 8 行——不是巧合，是两个口径。

### 1.7 病灶六：space 口径不一致（团队场景）

- 时间线在 `space=all` 走 `memoReadScope`：自己的全部 + 团队 protected + 公开 normal（`team-permissions.ts:72-110`）
- 标签树在 `space=all`（即不传 space）走的是 `eq(memoTags.userId, user.id)`——**只有自己的**（`tags.ts:118-121`）

**净效果**：在「全部」视图下，时间线能看到团队和公开笔记，但侧栏标签树只统计自己的。数字与内容对不上，且团队用户无从察觉。

### 1.8 侧栏为什么「显得敷衍」

#### 实测：图标尺寸失控

在 mini 上运行中的 dev 实例里逐个体测量侧栏 `svg` 的实际渲染尺寸：

| 位置 | 实际尺寸 | 相邻文字 |
|---|---|---|
| 7 个功能导航项图标 | **24 × 24** | 14px |
| 「无标签」按钮 | **24 × 24** | 12px |
| 语言切换 | **24 × 24** | 14px |
| 导出 / 导入 | 16 × 16 | 14px |

标签行内部更乱，**同一行出现四种尺寸**：

- 折叠箭头 `h-3.5 w-3.5` → 14px（`flaremo-explorer.tsx:406`）
- 标签的 `#` 图标 → **24px**（`:420`，只给了 `shrink-0 opacity-50`，没有尺寸类）
- 标签文字 `text-xs` → 12px（`:421`）
- hover 浮现的铅笔 / 垃圾桶 `h-3 w-3` → 12px（`:434`、`:443`）

**根因**：侧栏是全项目**唯一没有图标尺寸约束**的地方。其他所有 UI 组件都带一条把裸图标压到 16px 的规则：

```
[&_svg:not([class*='size-'])]:size-4     ← button.tsx / badge.tsx / dropdown-menu.tsx / tabs.tsx ...
```

侧栏用的是裸 `<button>` / `<Link>`，继承不到这条规则，于是落到 lucide 的默认值 `24`。

24px 图标配 12px 文字是 2:1；而项目里 Badge 是 12 配 12、Button 是 16 配 14。**「肿」和「糊」不是错觉，是比例失衡。**

#### 这个组件从未被设计过

历次 UI 打磨文档里，标签树的处置都是四个字——「现状保留」：

> `docs/flomo-alignment-ux-refinement.md:70`：**标签树**（现状保留）

它是早期版本留下的组件，之后每一轮打磨都被跳过。具体缺口：

| # | 问题 | 证据 |
|---|---|---|
| T1 | **排序按字母序，不按使用频次**（中文按码点排，最常用的可能排最后） | `tags.ts:180-182` `localeCompare` |
| T2 | 全量渲染，无上限、无「显示更多」、无虚拟化 | `flaremo-explorer.tsx:469` `nodes.map` |
| T3 | 计数只在 `> 1` 时显示（单条标签无计数） | `:422` |
| T4 | 父节点显示**含后代**的聚合数，不显示各层分布 | `tags.ts:131-137` |
| T5 | 只显示路径末段，无 tooltip 显示完整路径 | `:376` `name.split("/").at(-1)` |
| T6 | 折叠状态不持久化，刷新即展开 | `:359` 组件内 `useState` |
| T7 | 重命名输入框缩进**写死** `1.5rem`，不随层级 | `:523` |
| T8 | 无右键菜单、无拖拽、无标签搜索 | 全 `apps/web/src` 无 `onContextMenu` |
| T9 | 位置在功能导航**之后**、页脚之前——侧栏视觉权重最低的角落 | `:295` |
| T10 | 顶部统计与树的行数口径不同（见 §1.6） | — |

## 2. 核心判断

### 2.1 标签处于「半属性化」——最贵的一种状态

对照两条彻底路线：

| | 文本权威（flomo 式） | 属性权威（独立实体式） |
|---|---|---|
| 标签定义在 | 正文里，是**唯一事实源** | 独立输入框 / 标签面板 |
| 结构化表 | 是正文的**投影** | 是**本体** |
| 删除标签 | 抹掉正文里的 `#tag` | 只解除关联，正文不动 |
| 好处 | 录入流畅，符合肌肉记忆 | 干净、可排序/配色/分组，与 Markdown 完全解耦 |
| 代价 | 必须把 Markdown 语法处理干净 | 录入多一步，正文里的 `#tag` 沦为死文本 |

**现状是两条路各走一半**：存储按属性做（`memo_tags` + `payload.tags`），写入按文本做（正则提取）。

半属性化最贵——两边的成本都付了，两边的收益都没拿到：既有正则的不可靠，又有「正文说一套、标签表说一套」的双源不一致。

### 2.2 关于「任务也应该是记录的属性」——建议维持现状

这一条与已定案的模型冲突，需要说清楚，以免在错误的方向上消耗。

`docs/concept-model.md` 定稿：**两个核心实体（记录、任务）、一道门（转为任务）**。判据是**能否被「完成」**——记录不能，任务能。红线第 2、3 条明确：

> 2. 记录永不携带任务状态字段；任务状态永远住在 `tasks` 表。
> 3. 不双向回写正文；跨界只有「转为任务」这一道显式动作。

理由是**生命周期不同**：任务可完成、可逾期、可挂项目、有状态机；记录无状态、以时间戳为骨。合成一个实体意味着两个生命周期塞进一张表，权限与索引都要重做（红线 5 明确不做「一切皆对象」的统一大表）。

**但你的痛感是真实的**，现状确实有硬伤（本次一并复核，证据见 §6.2）：

| # | 问题 |
|---|---|
| M1 | 「转为任务」只搬行文本，**不带日期、不带项目** → 新任务默认掉进「未分配 + 未排期」 |
| M2 | 任务完成后**不回写**笔记，笔记 checkbox 与任务状态会分叉，且**无任何机制提示分叉** |
| M3 | 笔记侧**不显示**任务状态（任务卡有「来自笔记」回链，反向没有） |
| M4 | 重复点击「转为任务」**不去重**，同一行可建出多个任务 |
| M5 | 任务**不支持标签**（`tasks` 表无 tags 列） |

**方向判断**：这些是「**桥太窄 + 双向完全隔绝**」，不是「该不该是属性」。`docs/time-task-mental-model-audit.md`（09-19，未实施）已给出正解——**加第二道门**（快速建任务 + 转换时携带日期），本方案与之对齐，不另起炉灶。

**本次审查的结论：维持「两个实体、一道门」，把力气花在加宽门上。** 建议在 `concept-model.md` 的决策记录里补一条，注明「任务降格为记录属性」已于 2026-09-19 复核并否决，避免重复讨论。

### 2.3 侧栏问题不是审美，是缺约束 + 缺设计

§1.8 的实测说明：观感差有两层原因——**技术上是继承不到全局图标约束**（一行 CSS 可修），**产品上是从未被纳入设计范围**（需要一轮真正的设计）。

把这两层混在一起谈，就会得出「侧栏要重做」的过重结论；拆开看，第一层是半小时的事。

## 3. 方案

### 3.1 路线选择（决策点 ①）

| | 路线 A：**正文为语法，标签为属性** | 路线 B：**标签完全脱离正文** |
|---|---|---|
| 正文里的 `#tag` | 保留，作为**输入语法** | 不再解析（沦为普通文本） |
| 标签的定义 | 结构化表（**唯一事实源**），由正文**单向物化** | 结构化表（唯一事实源），由标签面板直接编辑 |
| 录入 | 打字时自然带上 | 必须切到标签控件 |
| 存量数据 | **零迁移** | 需要处理全部正文里的 `#tag`（迁移或废弃） |
| 与 Markdown 的关系 | 必须把字面量隔离做对 | 天然无关 |
| 主要工作量 | 修物化链路（单源正则 + 编辑重算 + 字面量隔离） | 新标签编辑 UI + 侧栏重做 + 存量处置 |

**推荐 A。理由：**

1. **`#tag` 内联是这个品类的肌肉记忆**（flomo / Obsidian / 微博），也是本产品已完成对齐的方向（`docs/flomo-alignment-ux-refinement.md` 全文以 flomo 为参照系）。砍掉它会拖慢录入——而录入速度是这类产品的生命线。
2. **存储层已经是结构化的**，下游（层级、重命名、筛选、计数）全部健康。问题只在「物化」这一步做错了。**修物化远比迁 UI 便宜，且不产生存量问题。**
3. **「属性」与「正文里有 `#tag`」并不矛盾。** 属性的正确含义是「查询、重命名、筛选走结构化表」——这已经具备。把它与「正文不许出现」对立起来是伪命题：真正的病是**两套正则 + 永不重算**。

**同时采纳路线 B 的一个能力**：在笔记详情提供**显式标签编辑控件**（加/删标签），作为第二条输入路径。这不需要新概念——语音捕捉页已有现成先例（`capture-page.tsx:766-785`：逗号分隔的纯属性标签输入框，完全不碰正文）。

这样最终的模型是：

```
正文 #tag ──┐
            ├──→ memo_tags（唯一事实源）──→ 侧栏 / 筛选 / 计数
标签控件  ──┘        ↑
                 两条输入路径，同一个出口
```

### 3.2 无论选哪条路线，都必须先修的 P0

这四条与路线选择**无关**，属于纯实现缺陷：

| # | 修复 | 位置 |
|---|---|---|
| **F1** | **正则单源化**：提取规则收敛到一个包（`@flaremo/contracts` 或 `domain`），前后端共用；客户端只用于**高亮/补全**，不再决定入库值 | `memo.ts:10`、`tags.ts:61`、`tag-highlight.ts:8`、`tag-autocomplete.ts:10` |
| **F2** | **入库以服务端为准**：`createMemo` / `updateMemo` 一律用服务端提取结果；客户端传来的 `payload.tags` 只作为**候选**，与服务端提取结果取并集或直接忽略 | `memos.ts:137`、`memos.ts:734-736` |
| **F3** | **编辑重算标签**：更新路径默认从 `nextContent` 重新提取；显式标签（走标签控件）才覆盖 | `memos.ts:734-743` |
| **F4** | **提取时隔离 Markdown 字面量**：复用已有的 `splitMarkdownLiteralSegments`（`tags.ts:498`），让提取与改写用**同一套**字面量规则 | `tags.ts:58-69` |

附带两条低成本修复：

| # | 修复 | 位置 |
|---|---|---|
| F5 | `renameTag` 的 LIKE 加转义（复用 `escapeLike`） | `tags.ts:227`、`:265` |
| F6 | 统一标签计数口径（侧栏统计格与标签树用同一个数） | `flaremo-explorer.tsx:137` vs `tags.ts:138-183` |

F1–F4 合起来约等于「把物化链路做对」，是路线 A 的主体工作量，也是**任何路线都绕不开的地基**。

### 3.3 侧栏标签区块重做

分两层，先修约束、再做设计。

**第一层：补上图标尺寸约束（技术债，立即修）**

给侧栏的导航项与标签行加上与其他组件一致的约束：

```
[&_svg:not([class*='size-'])]:size-4      # 导航项（配 14px 文字）
[&_svg:not([class*='size-'])]:size-3.5    # 标签行（配 12px 文字）
```

预期效果：24px → 16px（导航）/ 14px（标签行），行高与节奏立刻回到与其他组件一致的水位。

**第二层：标签区块的信息设计（产品，需要拍板）**

| # | 建议 | 解决 |
|---|---|---|
| D1 | **排序改为「计数优先，同数按名称」**，与补全下拉的排序一致（`tag-autocomplete.ts:41-66` 已是 exact → startsWith → includes + count 降序） | T1 |
| D2 | **父节点显示「自身 + 后代」两段或只显示自身**，消除数字歧义 | T4、T10 |
| D3 | **加「显示更多」或折叠阈值**（如默认 20 条），避免长尾标签淹没侧栏 | T2 |
| D4 | **hover 显示完整路径 tooltip**（末段展示保留，减少视觉噪音） | T5 |
| D5 | **折叠状态持久化**到 localStorage（与 `flaremo.explorer.timeView` 同一模式） | T6 |
| D6 | **标签区块提到导航之上**（标签是本产品的核心组织手段，不该在视觉最末） | T9 |
| D7 | 计数显示策略：**全显示**（含 `1`），或用更弱的视觉区分，避免「有的有数字有的没有」的随机感 | T3 |
| D8 | 重命名输入框缩进随层级 | T7 |

**建议不做**（克制）：标签配色、标签图标自定义、拖拽排序、标签云——在核心链路修好前，这些是给错误的地基加装饰。

### 3.4 与任务相关的收口（对齐既有审查稿）

不新开方案，直接采纳 `docs/time-task-mental-model-audit.md` 的相关批次：

- **M2 是设计而非缺陷**：「任务侧不回写正文」是概念模型红线 3 的明确要求，**不应修改**。真正的缺口在 M3——
