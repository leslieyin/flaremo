# 任务 / 日历 / 记录：时间心智审查与收口方案

- 日期：2026-09-19
- 范围：记录（memo）与任务（task）的「时间」语义、创建入口、日历/项目视图、提醒链路
- 性质：审查 + 决策稿。**尚未实施**——本稿回答「当前是什么状态」与「应该收敛成什么」，实施需先拍 §5 的三个决策点
- 方法：四路并行只读深查（任务创建入口全集 / 笔记时间能力 / 提醒通知链路 / 日历与项目交互），主会话逐条复核关键源码

---

## 0. 结论先行

**当前不是「任务 + 日历 + 笔记」三块功能敷衍，而是「时间」这一个维度被拆成了三层互不连通的表示，用户被迫在层之间手工搬运。**

| 层 | 载体 | 谁在用 |
|---|---|---|
| ① 记录的创建时刻 | `memos.createdAt`（= `display_time` 别名），不可改 | 时间线排序、往年今日、每日回顾、日历「当天记录」只读层 |
| ② 任务的结构化日期 | `tasks.dueAt`（纯 `YYYY-MM-DD` 字符串，无时刻） | 日历落格、逾期判定、cron 提醒 |
| ③ 正文里的日期文字 | Markdown 纯文本（工具栏「插入日期」写 UTC 日期字符串） | 只有人眼。渲染层不解析、不建索引、不回链 |

三层之间**没有任何自动联通**：正文里的日期不会被识别；「转为任务」只搬运行文本、不搬运日期；没有日期来源的笔记无法在日历上找到自己。

用户口中的「时间标签不应该只是让时间上屏的东西」，精确对应层③：**它现在是纯装饰，因为它不属于上面任何一层。**

## 1. 现状盘点

### 1.1 任务的创建入口（穷举）

| # | 位置 | 触发 | 预填 | 缺口 |
|---|---|---|---|---|
| 1 | `/projects` 头部「新建任务」 | 按钮 → 对话框 | `project_id` = 当前选中项目 | 日期要手选；无项目时（0 项目）此路曾为死路，现已支持「未分配」 |
| 2 | `/projects` 看板空态 | 按钮 → 同一对话框 | 同上 | 同上 |
| 3 | `/calendar` 日面板快速添加 | 输入框回车 | `due_at` = 选中日 | **不带 project**；入口藏在右侧面板底部 |
| 4 | 时间线 memo 卡片的待办行 | hover 出现「转为任务」 | `source_memo_id`，标题取行文本 | **不带日期、不带项目**——新任务默认掉进「未分配 + 未排期」 |
| 5 | memo 详情页正文待办行 | 同 4 | 同上 | 同上 |

另有两条易误认的死路：composer 工具栏的「任务列表」按钮只插入 `- [ ]` 文本（不是任务）；spotlight 搜索能列出任务，但点击不跳转（App 未传 `onSelectTask`）。

**关键观察**：日面板快速添加不到 30 行外就是「快速记录」输入框——**用户在同一个面板里写「记录」和写「任务」，走的是两个互不相识的表单**。这是当前心智摩擦最集中的地方。

### 1.2 笔记侧的时间能力

- 工具栏「插入日期」（`memo-composer.tsx:537-553`）：插入 `new Date().toISOString().slice(0, 10)` 纯文本。**注意这是 UTC 日期**，北京时间 08:00 前点它会插入「昨天」。
- 无 `@日期` 补全、无日期快捷键、无自然语言解析（全仓无 chrono/date-fns/dayjs/luxon）。
- 正文里的 `[2026-09-25]`、「明天」、「@周五」在渲染层全部是普通文本，无样式、无链接、无索引。
- `display_time` 是 `createdAt` 的别名（Memos 兼容），**不可修改**；客户端 API 也不接受时间字段。
- 唯一的正文结构化改写先例：音频转写的 `#flaremo-t=` 时钟 → seek 按钮（`memo-content.tsx:143-191`）。**说明「正文语法升格为可交互元素」这条路在本仓已有成熟先例可复用。**

### 1.3 日历与项目视图

- 侧栏入口：往年今日 / 记忆漫游 / 语音记录 / 日历 / 记忆 / 项目 / 文章 / 时间线。**没有「今天」「收件箱」「任务」。**
- `/calendar`：月历 + 议程两种视图（**无周视图、无日视图**）两种。月历格显示任务标题（最多 2 个 +N），逾期红字、完成删除线；右侧日面板可勾选完成、下拉改期（今天/明天/+7/自选）、删除、拖拽到别的日期改期。
- 日面板的「当天记录」是**只读层**，只能跳详情或跳时间线；没有 due 的任务只在议程底部「未排期」折叠区纯文本出现，**不能从日历把未排期任务拖到某天**。
- `/projects`：左「全部任务」+ 项目列表 + 回收站，右三列看板。拖拽改状态/排序**仅在选中具体项目时可用**（「全部任务」下拖不动）。服务端按 `sort_order, created_at` 排序，**不是按 dueAt**。
- **无日期任务没有归属视图**：既不在日历（被跳过），也不在 mini 日历（只统计有 due 的），只能靠「全部任务」看板或议程折叠区找到。
- 数据截断暗雷：`listTasks()` 全仓调用方都没有传 `page_size`、也没有消费 `next_page_token`，服务端默认 30——**任务超过 30 条后，mini 日历、议程、看板、时间线任务搜索全部静默截断**。

### 1.4 提醒链路：到点什么都不发生

- 已有：站内收件箱（`memos_notifications`，四类：评论/提及/每日回顾/逾期）+ 完整自研 Web Push（VAPID + RFC 8291，SW `push` 事件已接）+ 账户页订阅开关。
- cron 每天 **03:17 UTC（北京 11:17）**跑一次：给「昨天及更早到期且未完成」的任务写一条逾期站内通知 + 按用户聚合一条推送。标题正文硬编码中文。
- **没有**：到点提醒（无定时器/alarm/DO）、当天早晨摘要、「今天到期」提醒、按任务单推、邮件提醒。`dueAt` 目前只有两个用途——**日历上落格**和**次日判逾期**。

### 1.5 一个直接 bug（可独立修）

日历日面板的「快速记录」（`calendar-page.tsx:486-506`）调用 `createMemo({content, visibility, source})`，**不带任何日期**——服务端固定用 `now`。于是：

1. 在月历上点 9 月 25 日 → 在日面板写「和 A 对齐方案」→ 记录创建于**今天**，跳到 25 日看不到它；
2. 日面板过滤用 `after:D before:D+1`，后端 `toUtcDayStart` 按 **UTC 日界**解析（`packages/domain/src/memos.ts:328-332`）——本地（UTC+8）每天 0:00–8:00 写的记录会落进前一个 UTC 日，**当天有 1/3 的时间桶错位**。

后果：用户以为「在 25 日写了东西」，系统记的是「19 日 11:20 创建」，且两个日期都可能偏。**这正是「时间只是上屏的东西」的最尖锐体现——连着日期选择的写入都不被尊重。**

## 2. 核心判断

### 2.1 「两个实体、一道门」的数据模型是对的，缺的是「第二道门」

概念模型（`docs/concept-model.md`）定的是「记录无状态、任务有状态、判据是能否被完成」。这条判据在数据层成立，但**在输入层不成立**：用户写下「周五前把合同发给律师」时，他并不知道自己在写「记录」还是「任务」——**这句话既是记录，也是行动**。

当前只有一道门的后果：

- 记录永远无法携带时间（除了创建时刻）；
- 想让它变成行动，必须显式「转为任务」，且转换后**丢失原文的时间信息**（因为时间只在正文文本里）——得到一个「未分配 + 未排期」的任务，用户要再去日历或项目里补两刀；
- 于是一条笔记的生命周期是：写 → 找行 → hover → 转 → 去日历补日期 → 去项目补归属。**单向升级的成本 5 步，用户当然选择「就在正文里写个日期文字算了」——这正是层③存在的真实原因：它是用户被逼出来的 workaround。**

### 2.2 时间应该有「记录时刻」与「事件时刻」两个位置

用户的心智里，一条笔记的时间有两个完全不同的含义：

| | 含义 | 例子 | 现状 |
|---|---|---|---|
| **记录时刻** | 我在什么时候写下它 | 19 日 11:20 写下这句话 | `createdAt`，正确、不可改 |
| **事件时刻** | 这句话说的是什么时候的事 | 「25 日要开会」「上周三和 B 吵了一架」 | **不存在**，只能塞进正文当文字 |

现在的系统只有前者，却把后者的全部表达责任推给用户。**「时间标签应该配好对应时间」要补的正是这个洞。**

同时，「事件时刻」有两种意图，产品上必须分开处理：

- **未来**（25 日要开会）→ 本质是行动/日程 → 应该有路径变成日历上的东西；
- **过去**（上周三……）→ 本质是记录的时间锚 → 应该让这条记录回到那一天（往年今日、漫游、日历当天层）。

### 2.3 没有「今天」，所以所有视图都是孤岛

用户日常问题的第一句永远是「我今天要做什么」。当前侧栏没有任何一个入口回答它：日历要自己找今天，项目看板是状态视图不是时间视图，mini 日历是雷达不是操作面。**建议把侧栏的「日历」升级为「今天」**（默认落今天、徽标显示今日任务数），日历仍然是它的完整形态——这不新增概念，只是给已有的东西一个正确的首屏。

### 2.4 提醒缺的不是基础设施，是调度语义

Web Push、SW、订阅表、VAPID 全都跑通了，缺的只是「什么时候推」。当前是「次日 11:17 汇总昨天逾期」——对用户而言这不是提醒，是**事后责备**。最小可用的提醒语义应当是：**当天早晨给一份「今天要做什么」的摘要**（一个 cron 改动的成本级），进阶才是按时刻推送。

## 3. 目标模型（提案）

**一句话：两个实体不变，两道门；时间在正文里可被结构化；日历是唯一的排期操作面；提醒从「次日逾期」改为「当天到点」。**

### 3.1 两道门

```
记录（memo）──[门①：携带日期转为任务]──→ 任务（task，dueAt 落格）
     ↑                                          │
     └──────────[门②：快速建任务]───────────────┘   （主 composer 一排快捷键直达）
```

- **门①**：现有「转为任务」保留，但转换时**把正文中的日期一起带走**（见 3.2）。转换后任务立刻出现在日历对应日子上——不再是「未分配 + 未排期」。
- **门②**：主 composer（时间线那个大输入框）增加「快速建任务」——输入标题 + 可选日期/项目，一处创建、直接落格。**理由**：用户在这里写下「周五前发合同」，不应该被要求「先发成记录，再 hover 转任务」。这道门不改变「记录无状态」的数据原则，只是让输入层不必先分类。

### 3.2 正文里的时间：可结构化的日期语法

**范围**：只在日期上做，不做自然语言解析（「明天下午三点」不做，理由见 §5.1）。

**形态建议**：`[[2026-09-25]]`（双链语法，与既有 `#tag` 高亮、`#flaremo-t=` 转写时钟的正文改写先例一致），渲染为可点击的日期 chip：

- 点击 chip → 跳到 `/calendar?date=2026-09-25`；
- 悬停/上下文菜单 → 「安排到这天」（建任务并预填该日 due）；
- 编辑器内插入日期按钮改为插入这个语法（而非现在的纯文本 UTC 日期）；
- 转换任务时，行内第一个 date chip 自动成为 `dueAt`。

**过去 vs 未来**：过去日期（如 `[[2026-09-17]]`）视为记录的事件锚——该记录出现在 17 日的日历「当天记录」层；未来日期视为排期意图——提示或直接提供「转为任务」。

**要不要落库**（决策点，见 §5.2）：两个方案

| 方案 | 做法 | 代价 | 收益 |
|---|---|---|---|
| **A｜落库** | `memos` 加一个可空 `event_date`，写入时若正文有 date chip 则同步存一份 | 一次 migration + 契约字段 + 两端（编辑器/SSR）同步规则 | 日历「当天记录」层与往年今日可直接按 `event_date` 查询；性能好；语义稳定 |
| **B｜不落库** | 只做文本层：解析、chips、转换时提取；日历层靠查询侧正则/LIKE 预筛 + 应用层精确匹配 | 零 migration；但每次日期视图要扫文本，SSR 分享页也要重复实现解析 | 数据层完全不动，符合「记录无状态」的最保守解读 |

**推荐 A**。理由：用户要的是「时间标签真的配上那个时间」——如果它不能决定这条记录在日历上出现在哪一天、在漫游里归到哪个 bucket，它就仍然是装饰。`createdAt` 仍是唯一的时间线骨架、仍然不可改；`event_date` 只是视图分桶维度，不进时间线排序。

### 3.3 日历成为唯一的排期操作面

- 「未排期」（无 dueAt 的任务）在日程视图里**可拖到某天**（现在完全拖不动，只能纯文本看）；
- 日面板的「快速记录」修复为「写入所选日期」（同时修 UTC 日界问题）；
- 日面板里「记录」与「任务」两个输入框可否合一：**一个输入框 + 一个「排上日程」开关**（默认关=记录，开=任务并取当日 due）。这是消灭 §1.1 表格里「两个表单互不相识」的最小改造。

### 3.4 提醒：当天摘要 → 到点

- **P0（纯 cron 改动）**：把每日维护的推送部分拆出，按用户本地时区的**早晨**（如 UTC+8 的 08:00）推一条「今天 N 件事」摘要 + 站内 `today_tasks` 类型；逾期通知保留但降级为摘要内的一个计数，而不是单独的责备式推送。
- **P1（需要调度粒度）**：`dueAt` 升级为可带时刻（`YYYY-MM-DDTHH:mm` 或保留日期 + 可选 `dueTime` 字段），cron 每 5–15 分钟跑一次，命中「今天到期且未完成」的按用户聚合推送。**不做 per-task exact-time alarm**（成本与收益不匹配，见 §5.3）。

### 3.5 顺手要清的账（与本主题直接相关，几乎零产品风险）

1. 任务列表 30 条静默截断（`listTasks` 分页无人消费）——日历、mini 日历、议程、看板全部受影响；
2. 「全部任务」看板拖拽不可用（当前只在选中具体项目时启用）；
3. 任务列表默认排序按 `sort_order, created_at` 而非「日期优先」——今天该做什么排不出来；
4. spotlight 里点任务不跳转（未接 `onSelectTask`）；
5. 任务没有回收站专属视图（藏在项目页左下的折叠区，且只能恢复不能彻底删）。

## 5. 待拍板

### 5.1 正文时间语法：只做日期，还是也做自然语言？

- **建议只做结构化日期语法**（`[[2026-09-25]]` / 日期 chip 插入）。自然语言解析（「明天下午三点」）不做——中文解析的边界情况太多，误判代价是「静默排错期」，比不做更糟。
- 若要自然语言，建议往后放，且只作为**输入辅助**（把「明天」当场转成 chip 再存入），绝不常驻解析正文。

### 5.2 date chip 是否落库（`memos.event_date`）？

- **推荐落库**（方案 A）：日历/回顾/漫游的查询都靠 SQL，不落库意味着每个消费点都要在文本上跑解析（含 SSR 分享页），且解析规则一变历史数据的呈现就变。
- 若坚持「记录零新字段」的保守解读，方案 B 可行但需要接受性能与一致性代价。

### 5.3 提醒粒度：到日期（当天摘要）还是到时刻？

- **建议分两步**：先做「当天摘要」（B5 前半，零模型改动，立刻消除「事后责备」）；时刻级提醒（`dueTime` 字段）看真实使用反馈再定——它会把 `dueAt` 从日期升级为时间戳语义，影响日历落格、逾期判定、拖拽改期的全部现有逻辑，是**本稿中唯一的破格改动**。

## 6. 与既有决策的关系

- 不冲突：`dueAt` 仍是日程唯一事实源；记录仍不携带任务状态；仍不双向回写正文；「转为任务」仍是唯一的状态转换门（本稿只是让它带上日期）。
- 需要概念模型增补一处：「记录」定义加一句——**记录可有「事件时刻」（可空），但不可有状态**；判据仍是「能否被完成」。相应地，红线 2「记录永不携带任务状态字段」保持不变（`event_date` 不是状态）。
- 相关既有文档：`docs/concept-model.md`（两实体一道门）、`docs/projects-tasks-audit.md`（09-17 审查，本稿 §3.5 的多数条目是当时被列为 P2 后未做）、`docs/product-requirements.md`（R10 日历）、`docs/flomo-alignment-ux-refinement.md`（输入体验）。
